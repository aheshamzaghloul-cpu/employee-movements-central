# دليل اعتماد وتشغيل الإصدار v68.65.0

## هدف الإصدار

تأمين ملفات استيراد Excel المؤقتة وحذف الجلسات المتروكة بعد مدة محددة، مع الحفاظ على تحسينات الأداء والاختبارات من الإصدارات السابقة.

## متطلبات اعتماد ما قبل النشر

1. شغّل GitHub Actions على فرع الإصدار. يجب اجتياز اختبارات Flask وPostgreSQL، واختبارات العقود، وبناء صورة Docker، واختبار `/healthz` وصفحة الدخول ومحرك OCR المحلي.
2. في staging، اختبر تدفق Excel كاملًا: رفع الملف، ربط الأعمدة، المعاينة، اختيار صفوف الإضافة/التعديل، إلغاء صفوف، انتهاء صلاحية المراجعة، ثم التأكد من أن العملية ذرية عند الخطأ.
3. تحقق من أن مجلد `/tmp/employee_movements_excel_imports` مملوك لمستخدم التطبيق وبصلاحيات `0700`، وأن ملفات `.xlsx` و`.json` بصلاحيات `0600`. لا تُستخدم ملفات Excel المؤقتة لأكثر من ساعتين دون نشاط، وتُنظف الملفات المتروكة دوريًا.
4. نفّذ اختبار الأدوار على القراءة العالمية والتعديل المقيد بالمحافظة والروابط المباشرة وطلبات تعديل المأموريات المغلقة.
5. اختبر صور التيكيت على بيانات تجريبية معتمدة وتأكد من الحقول التي تحتاج مراجعة يدوية، ثم اطبع PDF وتحقق من ظهور المرفق.
6. أنشئ نسخة PostgreSQL احتياطية وتحقق من ملف الأرشيف وSHA-256، ثم استعدها إلى قاعدة معزولة باستخدام `scripts/restore.sh` أو `pg_restore --single-transaction`، وقارن عدد السجلات والمرفقات.
7. قِس زمن البحث والتقارير والتصدير باستخدام بيانات ممثلة، ثم راجع التصميم على الحاسوب والهاتف.

## النشر والتراجع

- لا تُجرِ نشرًا إنتاجيًا قبل أن يكون لديك نسخة احتياطية حديثة مجرّبة الاستعادة.
- لا تُعدّل متغيرات الأسرار داخل ملفات المشروع؛ استخدم إعدادات البيئة في مزود الاستضافة.
- عند فشل staging، احتفظ بسجلات CI والحاوية، وأصلح سبب الفشل قبل إعادة المحاولة.
- عند التراجع، أعد إصدار التطبيق السابق وفق آلية النشر، واستعد قاعدة البيانات فقط إذا استلزم التغيير مخططًا أو بيانات ولا يمكن التراجع بأمان. لا تستعد قاعدة الإنتاج بشكل آلي دون مراجعة واعتماد.

## حدود التحقق الحالية

الاختبارات المحلية لهذه الدفعة تشمل فحوص عقود ومساعد ملفات مستقل؛ لم يتم تشغيل Flask/PostgreSQL/Docker الحي أو GitHub Actions من جلسة المراجعة. لذلك هذا الدليل لا يمثل تصريحًا بالاعتماد النهائي.
