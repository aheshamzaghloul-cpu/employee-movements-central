# تقرير إعادة تصميم نماذج الحركات والمأموريات — v68.23.2

## النطاق

هذه المرحلة تعيد تصميم أربعة مسارات واجهة مرتبطة بالتشغيل اليومي، اعتمادًا على القوالب الفعلية لـJinja2 وملفات CSS/JavaScript الفعلية:

| المسار/العائلة | القالب | ما تمت مراجعته |
|---|---|---|
| صفحة الحركات | `templates/movements.html` | اختيار المحافظة والفرع والموظف، إنشاء الحركة، فلاتر السجل والحركات السارية والمتابعة |
| تعديل حركة | `templates/movement_edit.html` | تبديل نوع الحركة، بيانات الفرع والجهة، الانتداب المفتوح، حساب المدة، الإلغاء والحفظ |
| تعديل المأمورية | `templates/mission_edit.html` | المحافظة والفرع المستهدف، تواريخ البداية والنهاية، حفظ المسودة/المأمورية المفتوحة |
| مراجعة طلب تعديل مأمورية | `templates/mission_edit_request_review.html` | بيانات الطلب السابقة، وجهة المأمورية، التواريخ، الحالة النهائية وملاحظات Manager |

أضيفت ورقة `static/css/pages/movement-forms.css` ويتم تحميلها في `base.html` فقط لمسارات الحركات وتعديل المأموريات ومراجعة الطلبات. حُفظت أسماء الحقول المرسلة ومسارات POST وحقول CSRF لتقليل مخاطر تغيير العقود الخلفية.

## الإصلاحات الرئيسية

1. **قواعد تواريخ متوافقة مع نوع الحركة.** في نموذج الإنشاء، تاريخ البداية ونهاية الإجازة مطلوبان للإجازة، وتاريخ بداية الانتداب مطلوب، وتاريخ نهاية الانتداب مطلوب فقط عندما لا يكون الانتداب مفتوحًا، وتاريخ الإذن مطلوب للإذن فقط. حقل نهاية الانتداب المفتوح يُخفى ويُعطّل ويُفرّغ حتى لا يرسل التاريخ القديم.
2. **تعديل الحركة.** عولج التعارض بين منطق القالب و`app.js` الذي كان يعيد جعل نهاية الانتداب المفتوح إلزامية. عند إلغاء خيار الانتداب المفتوح يعود حقل النهاية إلى الظهور والإلزام.
3. **تعديل المأمورية.** بقي تاريخ النهاية اختياريًا لأن السجل قد يمثل انتدابًا مفتوحًا؛ ويجري رفض تاريخ نهاية يسبق البداية على مستوى المتصفح، مع استمرار تحقق الخادم.
4. **مراجعة Manager.** أصبحت نهاية المأمورية مطلوبة عند اختيار الحالة النهائية «مغلقة»، واختيارية عند «تحت التحرير»، وهو ما يتطابق مع تحقق الخدمة `validate_and_execute_mission_edit_request`.
5. **عدم حجب الإرسال بسبب حقل مخفي.** عند تبديل نوع الحركة بعد إدخال تاريخ نهاية غير صحيح، تُمسح قيود `min` ورسالة `setCustomValidity` من الحقل غير النشط؛ وبذلك لا يمنع خطأ إجازة مخفي تسجيل إذن صحيح أو يمنع خطأ انتداب مخفي تسجيل إجازة.
6. **تخطيط الهاتف.** إزالة تراكب شريط الإجراءات فوق الحقول، وإصلاح تجاوز عرض الوثيقة الناتج عن القائمة الجانبية المغلقة التي تُنقل خارج الشاشة. طبقة `html` تقص الزيادة الأفقية دون تغيير الأبعاد أو أسماء عناصر النماذج.
7. **وضوح وإتاحة.** مراجعة تسميات الحقول وربطها بمعرّفاتها، ورسائل الحالة الحية، وتقسيم النماذج إلى أقسام معنونة، وإظهار توضيحات قصيرة بجانب الحقول ذات السلوك الشرطي.

## نتائج الاختبارات

- **اختبارات العقود:** 168 اختبارًا تم جمعها واجتيازها في `contract_tests`.
- **اختبارات Chromium المعزولة:** 12 حالة عرض وثيقة عند 1440×900 و390×844 و320×700، موزعة على إنشاء/سجل الحركات، وتعديل الحركة، وتعديل المأمورية، ومراجعة المدير. لا توجد زيادة في `documentElement.scrollWidth` في أي حالة.
- **سلوك الإنشاء:** حُمّلت بطاقات الفروع والموظف عبر استجابات API وهمية؛ اختُبرت تصفية الفروع لمحافظة الوجهة، وحالة الانتداب المفتوح، وإلزام تاريخ نهاية الإجازة ورفض الترتيب الزمني الخاطئ، واشتراط تاريخ الإذن.
- **سلوك التعديل:** عند فتح سجل انتداب مفتوح، حقل النهاية مخفي ومعطل وغير مطلوب؛ وعند إلغاء الخيار يعود الحقل إلى الإظهار والإلزام. تحقق التحقق الأصلي من التواريخ برسالة عربية.
- **سلوك مراجعة المدير:** نهاية التاريخ مطلوبة لحالة «مغلقة» وغير مطلوبة لحالة «تحت التحرير»، كما يُرفض ترتيب التواريخ غير الصحيح.
- **أخطاء JavaScript أثناء المعاينات:** 0.
- **Python:** `compileall` نجح.
- **JavaScript:** فحص `node --check` نجح لكل ملفات JS السبعة.
- **CSS:** تحليل ملفات CSS الأربعة لم يظهر أخطاء على المستوى الأعلى.

تفاصيل القياسات والسلوك في `INTERACTION_CHECKS_v68.23.2.json`. ومن نتائج التفاعل الإضافية: بعد إدخال تاريخ إجازة غير صحيح ثم التحويل إلى إذن، تصبح كل الحقول المخفية غير معيقة للتحقق وتظل صلاحية النموذج صحيحة عند إدخال تاريخ الإذن المطلوب.

## ما لم يتم التحقق منه

لم يُشغّل تطبيق Flask حيًا ولم تُنفّذ الكتابة إلى قاعدة بيانات. استُخدمت استجابات API وهمية وبيانات اصطناعية للمعاينات. لذلك لا تدّعي هذه الجولة تحققًا من PostgreSQL أو الصلاحيات الحية أو نجاح دورة POST كاملة. يجب تشغيل اختبارات `tests/` وCI على بيئة الاعتماديات الفعلية، ثم اختبار الحركات والمأموريات على قاعدة مرحلية غير إنتاجية قبل اعتماد الإصدار.

لم يتم النشر ولم تُغيّر قاعدة بيانات الإنتاج.
